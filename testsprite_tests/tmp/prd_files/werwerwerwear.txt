1) Product Overview

Ovlink is a link management platform designed to help users convert long URLs into short links, manage those links, track click analytics, and reduce abuse through security and moderation workflows.

2) Problem Statement and Value Proposition

Problem: Long links are inefficient to share, hard to manage, and often unclear from a security standpoint.
Solution: Short-link generation + optional password/limits/expiration + reporting + moderation + user dashboard.
Value: Fast link creation, controllable distribution, measurable performance, and a security-first experience.

3) Objectives

H1: Reduce short-link creation time to under 10 seconds.

H2: Maintain a redirect success rate of ≥ 99%.

H3: Make abuse reports visible and manageable through moderation.

H4: Provide consistent UX with multi-language support (AZ/TR/EN) and theming.

H5: Maintain advertising/policy compliance via public policy & trust pages.

7) Core User Flows
Link Creator Flow

Enters a URL on the homepage

Selects optional settings

Receives the short link

Generates/downloads QR code

Manages links via the dashboard

Visitor Redirect Flow

Opens /:short

Sees a consent screen

Selects YES and proceeds after a countdown

If password-protected, verifies via /proceed/:short

If valid, redirects to the destination URL

Moderation Flow

User submits a report

Admin reviews reports

Admin marks as safe / disables / deletes the link

If needed, takes action at domain/user level

Custom Domain Flow

User adds a domain

Completes DNS verification (TXT + CNAME/A/AAAA)

Once verified, the user can select that domain when creating links

9) Business Rules

Unauthenticated users are subject to a daily link creation limit.

Short code format is restricted: A–Z, a–z, 0–9, _ -, max length 50.

Reserved route names cannot be used as aliases.

Disabled or policy-violating links must not redirect.

If consent is denied, the redirect flow must stop.

Redirect tracking must only be recorded if the redirect actually occurs.

A custom domain can only be used by the domain-owning user.

13) Security and Privacy Requirements

Do not send full IP addresses openly to users via email.

Redirect consent flow must be tamper-resistant using signed + timestamped validation.

Host header and proxy chain must be interpreted securely.

Disable caching on sensitive routes.

Policy text must not contradict collected data.

Abuse policy and Terms must be consistent and mutually supportive.

14) UX / Design Requirements

Public pages must remain consistent with a shared theme language.

Login/register/forgot/reset/proceed/error pages must follow a single design system.

CTAs must be explicit: “Create short link”, “Send to QR”, “Report”.

Dashboard actions must be visible and easily accessible.

Mobile-first responsive behavior must remain intact.

16) Risks

server.js has grown too large as a single file; high maintenance cost.

Mixed approach in routing and views (render + string HTML) creates technical debt.

Limited test coverage (primarily test/security-helpers.test.js).

SQLite may hit scaling limits under high concurrent traffic.

GeoIP-based country estimation may not always be accurate.

17) Definition of Done (DoD)

Critical user flows must work without interruption:

register → verify → login → shorten → redirect

Password-protected link flow

report → admin moderation

custom domain add → verify → active use

Additionally:

Public policy/trust pages must be accessible from the footer.

Language + theme switching must be consistent across all primary pages.

Security controls must be active.

Tests must pass cleanly: npm test.

18) Assumptions

Monetization (AdSense) policy text is not dynamically generated based on on/off status; it is managed at the content level.

The product is designed as a single-tenant B2C service.

Short-term priority: speed + security + UX stability; mid-term priority: scalability.
